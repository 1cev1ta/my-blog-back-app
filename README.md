# My Blog — бэкенд

Бэкенд для одностраничного приложения «Мой блог» (Яндекс Практикум, Middle Java-разработчик,
модуль 1, спринт 3). Проект написан на Spring Framework 6.2 без Spring Boot, собирается в WAR
и разворачивается в сервлет-контейнере Tomcat 10.1+ или Jetty 12+ (Jakarta EE 10). Данные
хранятся в PostgreSQL.

## Стек

- Java 21
- Gradle 8.14, Groovy DSL, плагин `war`
- Spring Framework 6.2: Spring Web MVC, Spring JDBC, Spring Data JDBC, Spring Test
- PostgreSQL 14+ для приложения, H2 для тестов
- Jackson, HikariCP, Logback
- JUnit 5, MockMvc

## Структура проекта

```
src/main/java/ru/yandex/practicum/blog
├── config      конфигурация Spring: корневой контекст, веб-контекст, база данных
├── controller  REST-контроллеры, DTO и обработка ошибок
├── service     бизнес-логика
├── dao         репозитории Spring Data JDBC и JDBC-реализации запросов
└── model       сущности, результаты поиска и модели представления
src/main/resources
├── schema.sql
└── application.properties.example
src/main/webapp/WEB-INF/web.xml
```

Приложение разделено на слои `controller → service → dao → база данных`. Контроллеры не
работают с SQL, а слой доступа к данным ничего не знает об HTTP.

## Требования

- JDK 21, переменная `JAVA_HOME` должна указывать на него
- PostgreSQL 14+ (подойдёт любой совместимый сервер)
- Tomcat 10.1+ для развёртывания

Для сборки и тестов PostgreSQL не нужен: тесты используют встроенную H2.

## Настройка

Скопируйте пример конфигурации и укажите свои параметры подключения:

```bash
cp src/main/resources/application.properties.example src/main/resources/application.properties
```

Файл `application.properties` добавлен в `.gitignore`, потому что содержит реальные учётные
данные. Коммитить его нельзя. Тестовая конфигурация лежит отдельно в
`src/test/resources/application.properties`, секретов не содержит и хранится в репозитории.

Переменные окружения имеют приоритет над файлом:

| Переменная         | Значение по умолчанию                   | Назначение            |
|--------------------|-----------------------------------------|-----------------------|
| `BLOG_DB_URL`      | `jdbc:postgresql://localhost:5432/blog` | JDBC URL              |
| `BLOG_DB_USERNAME` | `blog`                                  | пользователь БД       |
| `BLOG_DB_PASSWORD` | `blog`                                  | пароль БД             |
| `BLOG_DB_DRIVER`   | `org.postgresql.Driver`                 | класс JDBC-драйвера   |

Базу и пользователя достаточно создать один раз:

```sql
CREATE USER blog WITH PASSWORD 'change-me';
CREATE DATABASE blog OWNER blog;
```

Схема применяется автоматически при старте приложения: `schema.sql` выполняется через
`ResourceDatabasePopulator`. Скрипт идемпотентный, повторный запуск ничего не ломает.

## Сборка и тесты

```bash
# Windows
gradlew.bat clean test
gradlew.bat clean war

# Linux / macOS
./gradlew clean test
./gradlew clean war
```

Готовый WAR появляется в `build/libs/my-blog-back-app.war`.

## Развёртывание на Tomcat

1. Скачайте и распакуйте Tomcat 10.1+. Проверено на версии 10.1.61.
2. Скопируйте `build/libs/my-blog-back-app.war` в `%CATALINA_HOME%\webapps\`
   (или в `$CATALINA_HOME/webapps/`).
3. Убедитесь, что `JAVA_HOME` указывает на JDK 21, а параметры базы данных заданы.
4. Запустите Tomcat: `%CATALINA_HOME%\bin\startup.bat` (или `$CATALINA_HOME/bin/startup.sh`).

Tomcat не является полноценным application server, поэтому JDBC-драйвер должен быть доступен
контейнеру. По умолчанию драйвер PostgreSQL уже лежит в `WEB-INF/lib` внутри WAR. При
необходимости его можно дополнительно положить в `%CATALINA_HOME%\lib`.

После запуска бэкенд доступен по адресу
`http://localhost:8080/my-blog-back-app/api/posts`. Чтобы открыть его в корне контекста
(`http://localhost:8080/api/posts`), переименуйте WAR в `ROOT.war`.

## Запуск фронтенда

Архив фронтенда выдаётся отдельно в курсе. Распакуйте его, откройте терминал в каталоге
с `docker-compose.yaml` и выполните:

```bash
docker compose up -d
```

Приложение откроется по адресу `http://localhost/`. Фронтенд обращается к бэкенду напрямую
по `http://localhost:8080`, поэтому в `WebConfig` разрешены CORS-запросы с `http://localhost`
и `http://127.0.0.1` (в том числе с произвольным портом).

## REST API

| Метод  | Путь                                      | Описание                                              |
|--------|-------------------------------------------|-------------------------------------------------------|
| GET    | `/api/posts?search=&pageNumber=&pageSize=` | Страница постов с поиском и пагинацией                |
| POST   | `/api/posts`                              | Создать пост                                          |
| POST   | `/api/posts/{id}`                         | Получить пост (нестандартный метод, нужен фронтенду)  |
| PUT    | `/api/posts/{id}`                         | Обновить пост                                         |
| DELETE | `/api/posts/{id}`                         | Удалить пост вместе с комментариями                   |
| POST   | `/api/posts/{id}/likes`                   | Увеличить счётчик лайков и вернуть новое значение     |
| PUT    | `/api/posts/{id}/image`                   | Загрузить или заменить изображение (`multipart/form-data`, часть `image`) |
| GET    | `/api/posts/{id}/image`                   | Получить изображение поста                            |
| GET    | `/api/posts/{id}/comments`                | Список комментариев поста                             |
| GET    | `/api/posts/{id}/comments/{cid}`          | Получить комментарий                                  |
| POST   | `/api/posts/{id}/comments`                | Добавить комментарий                                  |
| PUT    | `/api/posts/{id}/comments/{cid}`          | Обновить комментарий                                  |
| DELETE | `/api/posts/{id}/comments/{cid}`          | Удалить комментарий                                   |

Все параметры ленты необязательные:

| Параметр     | По умолчанию | Описание                                                |
|--------------|--------------|---------------------------------------------------------|
| `search`     | `""`         | Строка поиска: теги `#тег` и слова из заголовка           |
| `pageNumber` | `1`          | Номер страницы, начиная с единицы, должен быть больше 0  |
| `pageSize`   | `5`          | Размер страницы, должен быть больше 0                    |

Ответ ленты выглядит так: `{"posts": [...], "hasPrev": bool, "hasNext": bool, "lastPage": n}`.
Значение `lastPage` всегда не меньше единицы.

Коды ответов:

| Ситуация                                                    | Код   |
|-------------------------------------------------------------|-------|
| Успешные `GET`, `PUT`, `DELETE`, лайки, скачивание картинки  | `200` |
| Успешное создание поста или комментария                     | `201` |
| Ошибка валидации: пустые поля, несовпадающие id, плохая пагинация | `400` |
| Пост, комментарий или адрес не найдены                      | `404` |
| Неподдерживаемый метод для существующего пути               | `405` |
| Непредвиденная ошибка сервера                               | `500` |

Тело ошибки всегда одинаковое:

```json
{ "status": 400, "message": "Post title must not be blank" }
```

Правила поиска:

- строка разбивается по пробелам, пустые слова отбрасываются;
- слова, начинающиеся с `#`, считаются тегами и объединяются через **AND**;
- остальные слова склеиваются через пробел и ищутся как подстрока заголовка без учёта регистра;
- фильтр по заголовку и фильтры по тегам объединяются через **AND**.

В ленте текст поста обрезается до 128 символов и дополняется многоточием `…`. На странице
поста возвращается полный текст.

## Тесты

В проект входят:

- unit-тесты разбора поисковой строки и обрезки текста;
- интеграционные тесты сервисов и DAO на H2 (`@SpringJUnitConfig`);
- MVC-тесты на `MockMvc` (`@SpringJUnitWebConfig`): посты, комментарии, лайки, изображения,
  поиск и пагинация.

Контексты Spring кэшируются: тесты сервисов и DAO используют один контекст, MVC-тесты другой,
поэтому за прогон контекст создаётся только дважды.

## Проверка

- `gradlew clean test war` — 34 теста, `BUILD SUCCESSFUL`;
- WAR развёрнут как `ROOT.war` на Apache Tomcat 10.1.61 с JDK 21 и проверен вручную: лента и
  обрезка текста, страница поста, создание, обновление и удаление, поиск по заголовку и тегам,
  лайки, комментарии, загрузка и скачивание изображения (байты совпадают), CORS preflight,
  ответы `400` и `404`, а также корректный UTF-8 при работе с кириллицей.

### Известная проблема фронтенда

При редактировании комментария фронтенд вызывает
`PUT /api/posts/{commentId}/comments/{commentId}`, то есть подставляет id комментария в
переменную пути `postId`. Бэкенд реализует контракт из задания
(`/api/posts/{postId}/comments/{commentId}`) и отвечает `404`, потому что поста с таким id нет.
